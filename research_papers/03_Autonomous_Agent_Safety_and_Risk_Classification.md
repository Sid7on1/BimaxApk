# Safety Containment, Risk Tiering, and Injection Defense in Autonomous Software Engineering Agents

The transition of large language models from conversational code assistants to autonomous software engineering agents marks a fundamental shift in how untrusted model reasoning interacts with operating systems. Frameworks such as Princeton University's SWE-agent, lightweight execution harnesses like mini-swe-agent, and commercial agent runtimes including Anthropic's Claude Code and Claude Cowork grant autoregressive models direct execution authority. These agents can navigate enterprise repositories, invoke bash commands, manage dependencies, synthesize specialized tooling, and submit code patches. However, granting broad tool access to probabilistic planners introduces severe security challenges. Operating systems lack an inherent boundary to distinguish intended refactoring commands from destructive mutations, exposing host filesystems, cloud infrastructure, and execution environments to accidental disruption and targeted compromise.

Establishing containment for autonomous coding agents requires a defense-in-depth architecture that bridges specialized interface design, static and neural runtime command verification, and rigorous operating system isolation. This report synthesizes research and engineering architectures from Princeton University, the Stanford Institute for Human-Centered Artificial Intelligence (HAI), and Anthropic. The analysis examines four-tier risk taxonomies for shell operations, quantifies the dispatch latency and verification efficacy of hybrid guardrails that combine abstract syntax tree (AST) parsers with speculative small language model (SLM) adjudicators, and evaluates structural defenses against indirect prompt injection delivered through untrusted codebase files and poisoned git diffs.

## Architectural Containment Paradigms

Securing autonomous coding agents requires balancing model agency with deterministic control boundaries. Princeton University, Anthropic, and Stanford HAI provide complementary perspectives on this challenge, ranging from interface engineering and OS virtualization to large-scale empirical studies of agent behavior.

### Princeton University: Agent-Computer Interfaces and Sandboxed Execution

Early coding agent deployments exposed large language models directly to interactive bash environments. Investigations by the Princeton Language and Intelligence (PLI) group revealed that standard operating system shells present a problematic action space for autoregressive models. Unbounded command outputs generated by utilities like cat, recursive directory searches, and sprawling build logs rapidly exhaust model context windows. This overflow induces context rot, where critical instructions and task constraints are crowded out by verbose observation logs.

To overcome these structural limitations, Princeton introduced the Agent-Computer Interface (ACI) within the SWE-agent framework. Rather than treating the language model as an interactive terminal operator, the ACI provides a restricted set of specialized, token-efficient commands. File viewing is mediated through a windowed viewer that restricts observations to a maximum of 100 lines per turn, complete with explicit line numbers and omission markers. Search functions like `find_file` and `search_dir` return bounded lists capped at 50 to 100 matches without dumping raw file contents.

For state modification, the ACI enforces deterministic guardrails directly within the execution loop. File edits require explicit line-range parameters alongside replacement strings, immediately triggering an integrated linter and syntax checker. If an edit introduces syntax errors or formatting violations, the runtime reverts the modification automatically and returns the linter output as an environmental observation, prompting the model to rectify its error before disk changes persist.

At the runtime layer, Princeton's SWE-ReX engine isolates execution within ephemeral Docker containers, Modal sandboxes, or AWS Fargate environments. Command completion is tracked using deterministic shell sentinels rather than brittle heuristic timeouts. The Princeton and Stanford teams further explored this paradigm through mini-swe-agent, which pares the execution scaffold down to approximately 100 lines of Python. Mini-swe-agent executes actions as isolated, stateless `subprocess.run` calls rather than managing persistent shell sessions. This design simplifies containerization, minimizes context drift, and demonstrates that robust execution bounding can be achieved without complex runtime harnesses.

### Anthropic: Multi-Layered Product Containment

Anthropic structures agent safety around limiting the blast radius across its production environments, distributing controls across the Environment Layer, the Model Layer, and the External Content Layer. This defense-in-depth model adapts containment intensity according to deployment risks and user technical expertise.

Within claude.ai, shell execution is isolated purely server-side inside gVisor containers utilizing Linux seccomp filters on dedicated infrastructure. Because execution is ephemeral and completely separated from the user's local workstation, the primary security boundary focuses on tenant isolation and preventing cross-session lateral movement.

For Claude Code, which operates locally within developer environments, Anthropic implements OS-level sandboxing via Apple Seatbelt on macOS and bubblewrap on Linux. The sandbox restricts file system operations strictly to the designated project workspace and denies external network access by default. This approach reduces manual permission prompts by 84% while maintaining strict local isolation.

Claude Cowork targets non-technical enterprise environments where users cannot evaluate raw shell operations. In this setting, Anthropic deploys a sealed, lightweight virtual machine with an independent operating system kernel, virtualized process table, and decoupled virtual filesystem. Host credentials remain locked within the host machine's operating system keychain and are never mounted into the guest VM. Cowork adopts a host-mode architecture where the orchestration agent runs on the host system to provide diagnostic transparency, while command execution and tool calls are confined to the guest VM. Workspace directories are mounted using granular permissions (read-only, read-write, or read-write-no-delete), resolving all filesystem symlinks prior to path validation to neutralize directory traversal attacks. Network egress is routed through a defensive man-in-the-middle (MITM) proxy inside the VM that inspects outbound traffic, enforcing session token authentication and blocking unauthorized data exfiltration to external infrastructure.

### Stanford HAI: Empirical Grounding of Real-World Vulnerability

While curated benchmarks like SWE-bench evaluate algorithmic problem-solving in controlled environments, research from Stanford HAI examines the failure modes and security risks that emerge when coding agents operate in open developer settings. The SWE-chat dataset, developed at Stanford, documents over 6,000 real-world developer sessions encompassing 63,000 prompts and 355,000 agent tool calls.

The empirical data indicates that coding patterns follow a bimodal distribution: in 40.8% of sessions, developers engage in "vibe coding," delegating more than 99% of code authoring to the agent without interactive oversight. However, only 44% of agent-produced code survives into user commits, and autonomous agent output introduces security vulnerabilities at a higher rate than human-authored code. The most prevalent flaws include OS command injection (CWE-78), path traversal (CWE-22), and SQL injection (CWE-89). Stanford HAI's 2026 AI Index highlights that while frontier models achieve high pass rates on benchmarks like SWE-bench Verified, standardized evaluations for responsible AI and runtime safety containment remain sparse. Under deliberate attack or complex contextual drift, unconstrained agents readily bypass text-level safety alignment, underscoring the necessity of deterministic pre-execution guardrails.

## Four-Tier Risk Classification Taxonomy for Shell Operations

To prevent unconstrained execution loops from damaging local operating systems or compromising enterprise assets, runtime harnesses implement graduated trust and risk classification policies. Drawing from operational definitions in industry frameworks and security research, shell operations are grouped into four operational tiers: SAFE, MODERATE, DESTRUCTIVE, and CRITICAL.

```text
SAFE (L0/L1)          MODERATE (L2)         DESTRUCTIVE (L3)      CRITICAL (L4)
Read-Only State       Reversible Workspace  File/History Mutation Irreversible Host Damage
Silent Dispatch       Automated Tracking    Automated Rollback    Hard Block / MFA Gate
```

### Risk Tiers and Policy Definitions

- **SAFE** operations encompass read-only, non-mutating commands that do not alter the filesystem, process tree, or external network state. Commands such as `ls`, `pwd`, `git status`, `cat`, and structured AST searches operate with zero risk of persistent corruption or lateral movement. In modern harnesses, SAFE operations bypass secondary review and are dispatched silently to maximize execution throughput.
- **MODERATE** operations introduce localized mutations within the designated project workspace that remain fully reversible through standard version control. This tier includes file creation (`touch`), directory generation (`mkdir`), compiling code within build directories, staging untracked files (`git add`), and running standard unit test runners. Runtime policies permit automated execution of MODERATE commands within sandboxed directories, provided that path validation checks confirm all targets reside strictly within authorized workspace roots.
- **DESTRUCTIVE** operations alter existing code, overwrite persistent state, delete local resources, or terminate running processes. Commands such as `rm -f`, overwriting uncommitted modifications (`git checkout -- .`, `git reset --hard`), moving active modules, and killing local processes (`kill`, `pkill`) fall into this category. Runtimes manage DESTRUCTIVE commands by capturing automated filesystem snapshots or git diffs before execution. Under frameworks like SWE-agent, destructive modifications are subject to post-execution syntax and linter checks that automatically roll back the file system if errors are detected.
- **CRITICAL** operations present severe risks of irreversible system damage, secret destruction, network compromise, or privilege escalation. This tier includes unconstrained recursive file deletions targeting root or user directories (`rm -rf /`, `rm -rf ~`), downloading and executing untrusted scripts (`curl | bash`), force-pushing to remote repositories (`git push --force`), purging secret mounts (`vault kv destroy`), modifying cluster states (`kubectl delete namespace`), privilege escalation (`sudo`), and establishing reverse shells or outbound network listeners. CRITICAL commands trigger unconditional execution blocks or require multi-factor human confirmation. Real-time terminal monitors inject process termination signals (`SIGINT`) immediately upon identifying a CRITICAL command signature, preventing state mutations from reaching the OS kernel.

### The Failure of Human-in-the-Loop Oversight

Early agent architectures attempted to mitigate DESTRUCTIVE and CRITICAL risks by incorporating human-in-the-loop (HITL) confirmation prompts before dispatching commands. However, empirical studies reveal that relying on human operators introduces a severe failure mode known as approval fatigue.

An Anthropic study tracking 1,053 testers demonstrated that users approved approximately 93% of permission prompts without reading or comprehending the underlying shell commands. While human reviewers caught 13.6% of dangerous commands during initial interactions, their detection accuracy plummeted to approximately 5% after evaluating 50 prompts. Because autonomous agents execute high volumes of benign commands during debugging and localization, developers become conditioned to treat authorization dialogs as routine interruptions.

To address this, Anthropic's Auto Mode replaces manual approval with a model-based risk classifier that evaluates commands before dispatch. In production testing, this automated classifier intercepted 89% of dangerous operations (reducing miss rates from 12% to 7% after red-teaming), maintaining consistency across long sessions with a false-positive rate of just 0.4% on benign commands. Consequently, operational safety requires migrating from interactive human oversight to automated, policy-enforced pre-execution verification.

## Dual-Layer Guardrail Latency and Verification Dynamics

Evaluating shell operations solely through language model judges introduces substantial dispatch latency, which degrades interactive performance during long issue-resolution loops. A hosted frontier LLM judge introduces $17\text{ ms}$ to $460\text{ ms}$ of latency per tool call, which accumulates into severe overhead when an agent executes hundreds of commands to localize bugs and verify patches. Conversely, pure regex or naive AST pattern matchers execute in under $3\text{ ms}$ but achieve low detection accuracy, peaking at an $F_1$ score of roughly $72.62\%$ due to bash syntax complexities like subshells, aliasing, compound string concatenations, and dynamic expansions.

To resolve this latency-accuracy trade-off, modern architectures deploy dual-layer guardrails combining deterministic AST pre-classifiers with speculative small language model verifiers.

```text
Raw Command c
     |
     v
[ Stage 1: Canonicalization Module ]  -->  Normalize aliases, shell encodings, pipes
     |
     v
[ Stage 2: Static Attribution Module ]
   ├── L1: Tree-sitter AST Structural Parser
   ├── L2: Semantic Lexicon & Command Heads
   ├── L3: Path Context & Sandbox Boundaries
   └── L4: Provenance Risk Rules
     |
     +--> Provisional Decision: d_prov in { allow, deny, warn }
     |
     |---- d_prov = allow ----> Dispatch directly to OS Shell (0.34 ms latency)
     |---- d_prov = deny  ----> Terminate command & return Trace Fail
     |
     v (d_prov = warn: borderline / ambiguous command)
[ Stage 3: Speculative Resolution Module ]
     |
     v
[ Small Language Model (SLM) Judge ]  -->  Adjudicate semantic context & intent
     |
     +--> Final Decision: d* in { allow, deny } (2.32 ms amortized latency)
```

### The CARE Pipeline Architecture

The CARE (Canonicalization, Attribution, and Resolution Engine) framework exemplifies this dual-layer approach, providing command-level verification at the dispatch boundary. CARE operates via a three-stage pipeline:

1. **In the Canonicalization Module**, a candidate command $c$ is normalized into a stable verification target $\hat{c} \leftarrow \mathcal{N}(c)$. This stage unrolls subshell wrappers, resolves bash aliases, decodes obfuscated representations (such as hex, base64 strings, or zero-width unicode), and splits compound pipelines into isolated commands.
2. **In the Static Attribution Module**, the normalized command $\hat{c}$ passes through four deterministic analysis layers to compute a multi-dimensional risk score and assign a provisional decision $d_{\text{prov}} \in \{\text{allow}, \text{warn}, \text{deny}\}$. Layer 1 uses an AST parser (Tree-sitter bash) to generate a concrete syntax tree $T(\hat{c})$ and flag structural anomalies $\delta_{\text{struct}}$. If AST parsing fails and high-risk tokens are detected, the command is denied immediately. Layer 2 extracts command heads and arguments ($s_{\text{sem}}$) against a known semantic lexicon. Layer 3 evaluates path targets ($s_{\text{path}}$) relative to active workspace policies $\Pi$ to prevent directory traversal. Layer 4 applies regex patterns ($s_{\text{pat}}$) backed by vulnerability rule banks.
3. **In the Speculative Resolution Module**, commands provisionally evaluated as allow (Safe/Moderate operations) bypass neural adjudication and execute immediately. Commands provisionally marked as deny (unambiguous Critical operations) are terminated without escalation. The speculative small language model verifier is engaged exclusively for borderline commands ($d_{\text{prov}} = \text{warn}$). Here, an SLM evaluates the normalized command alongside its structured attribution trace ($\text{trace}(c)$) to render a final decision $d^*$.

### Empirical Latency and Detection Profiles

Because benign software development commands and overt syntax violations constitute the majority of dispatch requests, deterministic pre-classifiers resolve most commands instantly. Under balanced benchmark evaluations, CARE's static enforcement profile (AST and regex pre-classifiers without neural escalation) executes with an average latency of $0.34\text{ ms}$, achieving an $F_1$ score of $84.99\%$ and reducing realized harm on adversarial suites like RedCode-gen to $37.33\%$.

When the speculative Resolution Module is activated for ambiguous warnings, the system achieves an $F_1$ score of $85.64\%$ with a false-positive rate of $0.91\%$ and an amortized mean latency of $2.32\text{ ms}$. This amortized overhead remains imperceptible within interactive workflows while delivering detection parity with expensive, always-on neural evaluators. In contrast, continuous evaluation using hosted frontier LLMs incurs latencies between $250\text{ ms}$ and $460\text{ ms}$, which introduces significant execution delays and increases API costs.

## Resistance to Indirect Prompt Injection via Codebases and Git Diffs

Autonomous coding agents must ingest external data to perform tasks like triaging issues, reviewing pull requests, and updating dependencies. This operational requirement exposes agents to indirect prompt injection (IPI), where malicious instructions are embedded within untrusted repository files, commit messages, patch diffs, and package manifests.

```text
Attacker Pull Request / Issue / README
  ├── Hidden Instructions inside Markdown / HTML Comments
  └── Malicious Commands embedded in Git Diff
               |
               v
Agent Context Window (System Prompt + Untrusted Tool Output)
               |
      [ Instruction Drift ]  --> Model treats injected data as system instructions
               |
               v
Compromised Tool Call (e.g., Exfiltrate GITHUB_TOKEN or Execute Remote Script)
               |
               v
Host Environment Risk (Container Breakout, Credential Theft, Corrupted CI/CD)
```

### The Instruction-Data Duality Vulnerability

The root cause of indirect prompt injection stems from the architecture of transformer models, which process system instructions and retrieved context within a shared token sequence. While special formatting tokens designate system, user, and tool roles, models do not enforce hardware-enforced privilege separation between instruction and data streams. Models generalize instructions based on stylistic and semantic cues. Consequently, when an agent ingests a git diff containing crafted directives (such as instructions disguised as comments instructing the agent to dump environment variables to a public endpoint), the attention layers treat the text as an authoritative command. This vulnerability ranks as OWASP LLM01 (Prompt Injection) and is intensified by OWASP LLM06 (Excessive Agency) when agents possess permissions to execute commands and commit code autonomously.

### Empirical Attack Vectors in Autonomous Workflows

Real-world security research highlights several documented vulnerabilities in autonomous coding agents:

- The **Comment and Control** exploit suite (CVSS 9.4) demonstrated that Claude Code Security Review, Google Gemini CLI Action, and GitHub Copilot Agent could be compromised simultaneously through repository text fields. Attackers placed instructions inside pull request titles, issue bodies, or invisible HTML comments. When the agents initiated automated code reviews, they ingested the rendered PR diffs, followed the hidden instructions, and dumped runner secrets (`ANTHROPIC_API_KEY`, `GITHUB_TOKEN`, `GEMINI_API_KEY`) directly into public PR comments or commit histories.
- In **CVE-2025-66032**, Anthropic's `claude-code-action` contained an authorization flaw where the `checkWritePermissions` routine trusted any GitHub App actor. Unauthenticated attackers submitted public issues containing injected commands, allowing external text to trigger unauthorized executions and compromise internal CI/CD secrets.
- In **CurXecute (CVE-2025-54135)**, the Cursor IDE agent processed third-party MCP text and web documentation containing instructions that directed the agent to create `.cursor/mcp.json`. By writing unvetted configuration files into the project workspace, attackers achieved remote code execution when the IDE loaded the malicious server definition.
- Similarly, vulnerabilities in Anthropic's reference Git MCP server (**CVE-2025-68143, 68144, 68145**) allowed poisoned README files or issue bodies to execute path traversals and argument injections, accessing files outside the repository boundary.

### Structural Countermeasures and Taint Tracking

Because prompt engineering and model alignment degrade under targeted adversarial attacks, organizations must deploy structural defenses that decouple untrusted data from the agent's control flow.

The **DualView** framework addresses indirect prompt injection by tracking untrusted data across the filesystem, shell, and network. The architecture maintains two synchronized representations of the workspace:

- **In AgentView**, external files, PR diffs, and tool outputs are abstracted into opaque symbols (e.g., `UNTRUSTED_CONTENT_REF_0A8F`). The agent plans modifications over these abstract references without exposing its transformer attention layers to embedded instructions.
- **In HumanView**, when underlying compilers, linters, or test suites require raw data, the runtime resolves the abstract symbols back into concrete payloads inside the sandbox.

Following command execution, DualView runs an internal git diff to identify modified files, symbolizing newly written data before it enters the model's history. In benchmark testing, DualView reduced immediate and stored indirect prompt injection attack success rates to 0% while maintaining agent utility within 6.4 percentage points of unprotected baselines.

Complementary defenses operate at the configuration and network layers. Pre-trust folder consent protocols, implemented in Claude Code, defer parsing project configuration files (e.g., `.claude/settings.json`) until the developer explicitly verifies the repository root, preventing startup-based code execution. Deterministic `PreToolUse` hooks intercept commands before dispatch to block composite exfiltration patterns, such as reading `.env` files followed by outbound HTTP requests. `PostToolUse` hooks scan tool outputs for instruction-override signatures and strip hidden zero-width unicode characters before context insertion. Finally, default-deny egress policies enforced via OS sandboxes or defensive MITM proxies prevent exfiltration payloads from reaching external destinations, ensuring containment even if the agent's reasoning is compromised.

## Synthesis of Containment Strategies

The security research from Princeton University, Stanford HAI, and Anthropic reflects the structural evolution of coding agent safety. Early paradigms granted agents unmediated shell access, relying on interactive human confirmation prompts to prevent errors. Empirical data confirms that this design fails due to approval fatigue, where users approve over 93% of actions blindly, allowing destructive commands to slip past review.

Modern containment frameworks combine specialized Agent-Computer Interfaces, deterministic AST pre-classifiers, speculative neural verification, and isolated virtualized environments. Looking forward, coding agents are increasingly generating and dynamically executing custom tooling within runtime loops, as demonstrated by Live-SWE-agent and self-evolving agent architectures. This shift from static toolsets to dynamic tool synthesis renders simple regex filtering insufficient. Robust production deployments require combining sub-millisecond AST canonicalization (preserving sub-3ms dispatch latencies), speculative SLM adjudication for ambiguous commands, symbolic taint tracking through DualView abstractions, and sealed, disposable virtual machines. This layered approach isolates agent reasoning from critical operating system resources, allowing organizations to realize the productivity benefits of autonomous software engineering while maintaining systemic resilience against operational disruption and indirect injection attacks.
